# 日々のしおり — My News

iPhoneで読みやすい、日本語のニュースリンク集です。Macへのインストール、ターミナル、有料API、APIキーは不要です。作業と設定はCodexクラウドとGitHubのブラウザ画面だけで行えます。

## 今の状態

GitHub Pagesで公開済みです：<https://hy-app-web.github.io/my-news-app/>。`PAGES_ENABLED=true` の既存設定を維持します。ユーザーがRSS収集成功とiPhoneの記事一覧・リンク動作を確認済みです。

今回の変更は、最新の `origin/main` を取得して新しい変更ブランチで作成しました。既存の実ニュースJSONとキャッシュを変更せず引き継ぎます。マージまでは本番の収集時刻・処理は変わりません。テスト用の記事は `tests/` と一時ディレクトリ内だけで使い、公開データに追加しません。

## できること

- AI、テクノロジー、ビジネス、経済、バズ、グルメ、イベント、東京、沖縄、ハンドメイドの複数選択。
- 選択テーマの**いずれか**に該当する記事を表示（OR条件）。選択なしは全件。「すべて表示」で解除。
- 選択内容をこのブラウザのlocalStorageに保存。保存できない環境でも絞り込みは可能です。別端末・別ブラウザとは同期されず、ブラウザデータ削除で消えます。
- RSS掲載日時の新しい順、元記事URLによる重複除外、複数テーマの統合。
- 見出し、配信元（元記事のドメイン）、日時、元記事リンク、最終更新日時。
- 読み込み失敗、記事なし、収集失敗、48時間以上の更新遅延の案内。
- iPhoneホーム画面用のmanifest、PNGアイコン、Apple用メタ設定。

通知機能・通知ボタンはありません。Service Workerやオフライン配信もありません。ホーム画面から開く場合も通信が必要です。

## 情報取得元と利用条件の確認

確認日：2026年11月16日（日本時間）。公式の次の案内を確認してRSSを選びました。

- [はてな利用規約](https://policies.hatena.ne.jp/rule)：権利侵害・過負荷などの禁止事項と各ヘルプを確認。
- [過剰アクセスに関する注意事項](https://b.hatena.ne.jp/help/entry/notice_access)：HTML巡回ではなくRSS/APIの使用を案内。特定フィードへの取得は多くても30分ごと程度とされているため、通常は1日2回、手動の連続実行も保存済みの試行時刻で30分以内の再取得を抑えます。
- [公式開発ブログ：タグ検索RSS](https://bookmark.hatenastaff.com/entry/2019/09/12/191844)：`/search/tag?q=...&mode=rss` の形式を確認。

### 使うフィード

取得元はすべて **はてなブックマーク** です。各テーマについて `https://b.hatena.ne.jp/search/tag?q=テーマ名&mode=rss&sort=recent` を取得します（URLエンコードはスクリプトで処理）。「バズ」だけは総合人気エントリー `https://b.hatena.ne.jp/hotentry.rss` を使います。一覧とURLは `scripts/collect_news.py` の `FEEDS` にあります。

収集スクリプトは本文、画像、ユーザーコメント、ブックマーク数を保存しません。要約は別途、Codexの定期タスクが確認できた内容だけを短くまとめます。RSSに含まれる見出しと元記事URL、日時のみを取り出し、配信元ドメインとテーマを付けます。元記事のページは取得しません。元サイトとは別に情報取得元としてはてなブックマークをサイト内に表示します。

これは公式のRSS取得案内に従ったリンク集であり、各記事の転載許諾を取得したものではありません。記事の権利は各権利者に帰属します。利用条件が変わった場合は対象フィードを停止・変更してください。営利利用や本文等の再利用を加える際は別途条件の確認が必要です。

**表示の限界：** はてなブックマークのタグ検索にはブログや過去の記事も含まれ、各テーマを網羅するものではありません。分類はタグ検索由来で誤分類があり得ます。RSSの日時（`dc:date` / `pubDate`等）は元記事公開日時とは限らないため、画面では「RSS掲載日時」と表示します。公開日を推測したり、取得時刻を記事日時として補ったりしません。日時のない・不正な記事は除外します。

## 収集と障害時の動作

`.github/workflows/collect-news.yml` の **Collect news** が、**日本時間の毎日12時・18時**を目安に実行されます。cronは `0 3,9 * * *`（UTCの03:00・09:00）です。**GitHub Actionsの定期実行には遅延・未実行があり、時刻どおりの更新を保証しません。** 画面のニュース欄にも予定時刻と遅延の案内を表示します。スケジュールはデフォルトブランチのワークフローのみが対象です。公開リポジトリでは長期間活動がないとスケジュールが停止される場合もあります。

ブラウザから **Actions → Collect news → Run workflow → main → Run workflow** で手動実行できます。Macへのインストールや操作は不要です。1フィードあたり25秒のタイムアウト、最大2MB、最大80記事を取得候補にします。RSS収集はPython 3.12の標準ライブラリだけで動きます。

### 1回最大20件の追加とテーマの配分

- 全10テーマから今回取得できた候補を集め、既存記事のURLを除外し、テーマをまたぐ同一URLも1件に統合します。
- 今回追加する記事数が少ないテーマを優先し、同じテーマ内ではRSS掲載日時の新しい記事を優先します。同数の場合のテーマ順は既存URL数に応じて回転させます。
- 複数テーマに該当する記事は1件として追加し、配分の計算ではすべての該当テーマに数えます。
- **10テーマ合計で1回最大20件**。各テーマに十分な別記事があれば各2件ずつ、足りないテーマの枠は候補のあるテーマに回します。全体の新着不足時は取得できた未登録分だけ追加します。
- 過去の記事を削除・置き換えず保存し、RSS掲載日時の新しい順で一覧表示します。以前の「最新600件まで」の切り捨ては廃止します。既存記事の見出し・日時・テーマも書き換えません。
- 「新着」はこのアプリに未登録のURLという意味です。古い記事が今回初めてRSSに現れる場合もあります。

URLのフラグメント、`utm_*`、`fbclid`、`gclid` を除去して同一URLを判定し、他のクエリパラメーターは保持します。異なるURLで配信された同内容記事やHTTP/HTTPSの別URLまで同一とは判定しません。テーマごとの新着数や重複状況によって配分は偏るため、完全な均等配分は保証しません。

### 保存ファイルと失敗時の保持

- `docs/data/news.json`：蓄積した公開用ニュース。`updatedAt` は少なくとも1フィードを取得できた時刻です（追加0件でも更新）。`completedRunIds` は保存済みActions実行IDで、同じ実行の再試行で追加枠を再使用することを防ぎます。
- `docs/data/status.json`：最終試行日時、今回の追加件数 `addedCount`、テーマごとの成功・失敗・30分以内の取得抑制、最終成功日時。
- `collector-cache.json`：テーマ単位の前回取得データと試行日時。公開成果物 `docs/` の外に置きます。

一部のフィードが失敗しても全既存記事を残し、今回取得に成功したフィードの未登録記事だけを追加します。失敗・30分以内の取得抑制時に、古いキャッシュの未登録候補を追加することはありません。**全フィードが失敗または取得抑制された場合、news.jsonはバイト単位で保持**し、statusとキャッシュの試行状態だけ保存します。正常な空フィードは成功として扱います。全件失敗したActions実行は登録済みにしないため、時間をおいて同じ実行を再試行できます。

収集失敗でもstatus保存まで正常終了することがあります。サイトの案内・status・実行ログで確認してください。更新が2日以上止まった場合もサイトに案内します。

### 同時実行・再実行と公開連携

すべての定期・手動・再実行を共通の `collect-news` concurrencyグループで直列化し、実行中の処理をキャンセルしません。待機中の実行はGitHub側の仕様で置き換えられる場合があります。各収集ジョブは開始後に最新mainを再取得し、fast-forwardで取り込んでからデータを読みます。同じ作業ディレクトリで複数の収集プロセスが起動した場合もファイルロックで直列化します。

成功した実行の `GITHUB_RUN_ID` をニュース追加と同じJSONのatomic置換で保存し、同じIDの再実行では収集・追加をスキップします。その後に別実行があっても重複追加しません。別IDの新しい手動実行には新たな最大20件の枠がありますが、既存URLは毎回除外します。

保存は通常の `git push` のみで行い、強制pushや生成JSONの自動リベースはしません。収集中に他の変更でmainが進んだ場合、pushは安全に失敗してリモートのデータを保持します。この場合はActionsを再実行すると最新mainを元に追加を計算し直します。push失敗時は公開ジョブも開始しません。

**既存の公開方式を維持**し、収集ジョブの保存成功後に `publish` ジョブから再利用可能な `pages.yml` を直接呼びます。`GITHUB_TOKEN` のコミットでは別のpushワークフローが起動しないため、pushの連鎖に依存しません。Pages側はmainを取得して `docs/` を公開し、既存の `PAGES_ENABLED=true` 条件とPages環境・権限をそのまま使います。保存済み実行を再試行した場合も公開ジョブは呼ばれるため、ニュースを再追加せず公開だけを再試行できます。

公開サイトの表示更新は収集・コミット・Pagesデプロイの完了後になります。Pagesのみ再公開する場合は **Actions → Publish Pages → Run workflow** を使えます。このPRの作成時にはデプロイもマージも行いません。後でユーザーがマージすると、既存設定により画面の更新が公開され、新しい定期収集が有効になります。

収集コミットが拒否される場合はActionsログを確認してください。mainへの直接pushを禁止するブランチ保護や組織ポリシーでは、収集データ保存方式の調整が必要です。通常はワークフローに必要最小限の `contents: write` を宣言しているため、個人トークンは不要です。公開には `pages: write` / `id-token: write` を公開ジョブにだけ付与しています。

公開を止める場合、変数を `false` にすると今後のデプロイが止まります。すでに公開済みのサイトを削除する場合は **Settings → Pages → Unpublish site** を使用します（変数だけでは既存サイトは消えません）。

## Codexによる要約

画面の「ニュースの要約」は `docs/data/summaries.json` を読みます。収集Actions自体はAIを呼びません。外部AI APIやAPIキーは使わず、Codexの利用枠で定期タスクを実行する方式です。定期タスクはGitHub Actionsと別に登録が必要で、このコードだけでは自動要約は開始しません。

JSON形式：`{"schemaVersion":1,"editions":[{"editionId":"YYYY-MM-DD-18","generatedAt":"ISO8601","scheduledFor":"ISO8601","candidateCount":20,"skippedCount":0,"items":[{"id":"news.jsonのid","summary":"80〜150字程度の短い要約","basis":"本文","sourceUrl":"news.jsonと同じ元記事URL"}]}]}`。basisは「本文」または「説明文」。各回最大20件、最大14回分を保持し、同じeditionIdの再実行は重複登録しません。要約ファイルだけ更新し、news.jsonや収集キャッシュは変更しません。

見出しのみからの推測、読めない有料記事の回避、全文転載は行いません。検索結果の見出しだけしか得られない記事はスキップします。失敗時に架空の要約を作らず前回のファイルを保持します。無料のプラン内利用を優先し、クレジット購入・有料APIへの切り替えは行いません。プランの利用上限に達すると要約が更新されない場合があります。

フロントエンドは要約の文字数、根拠種別、記事ID・URL一致を検証し、HTMLを解釈せずtextContentで表示します。要約ファイルの欠落・破損でもニュース一覧は表示します。直近の回を選択テーマで絞り込み、24時間以上古い場合は前回の要約であることを表示します。
